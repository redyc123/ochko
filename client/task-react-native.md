# Задача: мобильное приложение О.Ч.К.О. на React Native

Ты пишешь мобильное приложение-компаньон для смарт-очков О.Ч.К.О. (дипломный проект «Разработка модульной платформы бюджетных смарт-очков на основе серийных компонентов»). Очки — навесной модуль на обычные очки: маленький OLED-экран, микрофон и одна кнопка. Вся «умная» часть живёт в телефоне, то есть в твоём приложении: навигация, уведомления, распознавание речи, LLM-агент, проверка голоса.

---

## 1. Что такое очки (чтобы понимать ограничения)

- Плата **Seeed XIAO ESP32-C6** (RISC-V 160 МГц, 512 КБ SRAM, без FPU), стек NimBLE.
- Экран **OLED 0,42″, 72×40 пикселей**, SSD1306. Шрифтом 6×8 помещается **12 символов × 5 строк ≈ 60 символов**. Кадр зеркалится в прошивке (изображение идёт через светоделитель), приложению об этом думать не нужно.
- Микрофон **INMP441**, 16 кГц. Звук приходит в телефон сжатым **IMA ADPCM** (4 бита на отсчёт, ~64 кбит/с) через GATT-уведомления.
- Одна кнопка **D1**: короткое нажатие — листать/скрыть, удержание — запись/подтверждение.
- Активация голоса: стартовое слово распознаётся на самих очках, кнопка — запасной способ.
- Аккумулятор маленький, цель автономности ≥ 3 ч. Поэтому **очки не должны получать лишних пакетов**: всё, что можно посчитать на телефоне, считается на телефоне, а в очки уходит уже готовая короткая картинка в виде данных.
- Прошивку пишут параллельно. **BLE-протокол из раздела 4 — это контракт**: прошивка подстроится под него. Если в процессе понадобится его изменить, меняй `docs/PROTOCOL.md` и номер версии протокола, а не «тихо» формат пакета.

## 2. Стек и общие требования

- **React Native + TypeScript (strict)**. Рекомендую Expo с dev client и `expo prebuild` (нативные модули обязательны, Expo Go не подойдёт). Если считаешь bare React Native удобнее — можно, но объясни выбор в README.
- Основная платформа — **Android** (демо на защите будет на нём). iOS должен собираться и работать в том, что iOS разрешает; ограничения iOS честно описать в README.
- BLE: `react-native-ble-plx` (или аналог с поддержкой MTU, bonding и notify).
- Геолокация: `expo-location` (или аналог) с работой в фоне.
- Секреты (API-ключи LLM/STT, отпечаток голоса): `react-native-keychain` / Android Keystore / iOS Keychain. Никаких ключей в коде и в `AsyncStorage`.
- Состояние: любой лёгкий стор (Zustand или аналог). Навигация по экранам: React Navigation или expo-router.
- Тесты: Jest для чистой логики (кодирование пакетов, разбор ответа роутера, детектор схода с маршрута, ADPCM-декодер). Целевое покрытие этих модулей — высокое, UI можно не тестировать.
- Линт и форматирование: ESLint + Prettier, `tsc --noEmit` без ошибок.
- Язык интерфейса — русский.

### Структура (ориентир, можно улучшать)

```
src/
  ble/          // подключение, сопряжение, очередь записи, протокол
    protocol/   // кодеры/декодеры пакетов — чистые функции, 100% тестов
  glasses/      // высокоуровневый API: showManeuver(), showText(), onButton()...
  emulator/     // эмулятор очков: рисует экран 72×40 в приложении
  nav/          // геокодинг, роутинг, ведение по маршруту

  audio/        // приём ADPCM, декодер, WAV

  agent/        // LlmProvider, адаптеры, инструменты
  voiceprint/
  screens/
docs/PROTOCOL.md
```

### Эмулятор очков (обязательно с первого этапа)

Прошивка может отставать, поэтому в приложении нужен **режим эмулятора**: вместо реального BLE пакеты уходят в виртуальное устройство, которое рисует на экране телефона увеличенный монохромный экран 72×40 ровно так, как его нарисует прошивка (тот же шрифт 6×8, те же иконки манёвров). Кнопка D1 эмулируется кнопкой на экране. Эмулятор декодирует **те же байты**, что уходят в очки, а не берёт данные напрямую из стора: так он заодно проверяет протокол.

## 3. Этапы

Каждый этап заканчивается проверяемым результатом. Делай их по порядку; внутри этапа — маленькими осмысленными коммитами.

### Этап 0. Каркас и подключение к очкам

- Сканирование по UUID сервиса О.Ч.К.О., подключение, запрос MTU 247.
- **Сопряжение с шифрованием**: LE Secure Connections + бондинг. Очки показывают 6-значный код на OLED (Passkey Entry, очки — DisplayOnly), пользователь вводит его в системный диалог. Все характеристики О.Ч.К.О. на очках закрыты флагами «только зашифровано и аутентифицировано», поэтому до сопряжения приложение их не прочитает — это нормально, обработай ошибку понятным сообщением.
- Автопереподключение к сопряжённому устройству, индикатор состояния (нет связи / подключено / заряд батареи).
- Экран «Устройство»: подключить, забыть, версия протокола и прошивки, переключатель «эмулятор».
- **Результат:** сопряжение с реальными очками или эмулятором, приложение показывает заряд и версию.

### Этап 1. Навигатор — срок 15 декабря 2026

Сценарий пользователя: «Говорю, куда мне надо, агент строит маршрут, на экране очков вижу, куда поворачивать».

**1.1. Ввод цели.**
- Три способа, все приводят к одной функции `navigateTo(query: string)`:
  1. Текстом в приложении.
  2. Голосом через микрофон **телефона** (системное распознавание или STT-провайдер из этапа 3). Это нужно, чтобы навигатор работал к сроку, даже если аудио с очков ещё не готово.
  3. Голосом через очки — подключается автоматически, когда готов этап 3 (агент вызывает инструмент `navigate_to`).
- Свободная фраза вида «отведи меня в Пятёрочку на Ленина» или «ближайшая аптека» превращается в запрос геокодера. На первом шаге можно без LLM (просто текст в Nominatim), с LLM — после этапа 4.
- Если найдено несколько вариантов, показать список в приложении (до 5), на очках — «Выберите цель в телефоне».

**1.2. Геокодинг: Nominatim напрямую (без MCP-прослоек).**
- `https://nominatim.openstreetmap.org/search`, `format=jsonv2`, `accept-language=ru`, `countrycodes=ru`, `limit=5`, `viewbox` вокруг текущей позиции с `bounded=0`, чтобы ближние результаты шли первыми.
- Соблюдай правила публичного Nominatim: **не больше 1 запроса в секунду** (глобальная очередь в приложении), осмысленный `User-Agent` с названием приложения и контактом, **никакого автодополнения по мере набора** (запрос только по кнопке «Найти» или по окончании фразы), кэширование ответов.
- Для «ближайшая аптека/кафе/банкомат» допустимо использовать Overpass API (поиск по тегу в радиусе) — по желанию, не обязательно к сроку.
- Базовый URL вынести в настройки, чтобы потом подставить свой сервер.

**1.3. Маршрут: Valhalla.**
- Профиль по умолчанию — **пеший** (`costing: "pedestrian"`), переключатели «пешком / велосипед / авто» в настройках.
- `directions_options: { language: "ru-RU", units: "kilometers" }`, получать `maneuvers` с типом, длиной, улицей, `begin_shape_index`/`end_shape_index`, и `shape` (polyline6).
- Для разработки и защиты — публичный демо-сервер (например, `https://valhalla1.openstreetmap.de/route`); базовый URL в настройках. Обработать ошибки сети и лимиты (повтор с экспоненциальной задержкой, понятное сообщение на очках).
- Роутер спрятать за интерфейсом `Router.route(from, to, profile) → Route`, чтобы можно было подставить OSRM или GraphHopper без переписывания остального.

**1.4. Ведение по маршруту (главная логика, вся на телефоне).**
- Подписка на GPS с высокой точностью, в фоне — через Android foreground service (тип `location`) с постоянным уведомлением «О.Ч.К.О. ведёт по маршруту». На iOS — фоновый режим location.
- Привязка позиции к линии маршрута (ближайший сегмент `shape`), расчёт: текущий манёвр, расстояние до него, оставшееся расстояние и время.
- Сглаживание: не дёргать экран от GPS-шума (порог изменения расстояния, медианный фильтр или фильтр Калмана — на выбор).
- **Сход с маршрута:** если отклонение > 30 м дольше 10 с (пороги в настройках), статус «Перестраиваю…» и перестроение от текущей точки. Не чаще одного перестроения в 15 с.
- **Прибытие:** ближе 15 м к цели → «Вы на месте», через несколько секунд экран навигации на очках гаснет.
- Потеря GPS > 10 с → статус «Нет GPS» на очках.
- Голосовые подсказки не обязательны (динамика в очках нет). Опционально — системный TTS телефона в наушники.

**1.5. Что уходит в очки.**
- Только компактные пакеты из раздела 4.4: «текущий манёвр» (иконка, расстояние, улица) и «прогресс» (только расстояние). Карты и полилинии в очки **не передаются**.
- Частота: пакет манёвра — при смене манёвра; пакет прогресса — когда расстояние изменилось на ≥ 5 м (или ≥ 10 % при расстоянии > 500 м), но не чаще 1 раза в секунду. При неизменном расстоянии ничего не слать.
- Расстояние на очках округлять по-человечески: < 100 м — с шагом 5 м, < 1 км — с шагом 10 м, дальше — «1,2 км». Округление делает приложение, очки печатают число как есть.
- Название улицы обрезать до 24 байт UTF-8 по границе символа (две строки по 12). Кириллица передаётся в UTF-8, шрифт с кириллицей — забота прошивки.

**1.6. Экран навигации в приложении.**
- Карта с маршрутом и текущей позицией (`react-native-maps` с тайлами OSM или MapLibre — на выбор), список манёвров, кнопки «Начать», «Стоп».
- Рядом — превью экрана очков (тот же рендер, что в эмуляторе).
- Атрибуция «© участники OpenStreetMap» на карте и в «О приложении» — обязательна по лицензии ODbL.

**1.7. Режим демо без улицы.**
- «Симуляция поездки»: позиция движется по построенному маршруту с заданной скоростью (5 км/ч, ускорение ×2/×5/×10). Нужен для защиты в аудитории и для отладки прошивки. Симулятор подменяет источник GPS, вся остальная логика работает как в реальности.

**Результат этапа 1:** на реальных очках (или в эмуляторе, если прошивка не готова) пешеходный маршрут проходит от начала до «Вы на месте», с поворотами, расстояниями и перестроением при сходе. В README — как запустить симуляцию.

### Этап 2. Уведомления (вместо Gadgetbridge)

На Android Gadgetbridge занимает BLE-соединение с очками, поэтому уведомления читает само приложение.

- Нативный модуль на Kotlin: `NotificationListenerService`, мост в JS (событие «новое уведомление»: приложение-источник, заголовок, текст, время, категория). Экран выдачи разрешения в системных настройках.
- Фильтры: белый список приложений, «не беспокоить» по расписанию, скрытие текста для выбранных приложений (показывать только «Новое сообщение»). SMS-коды по умолчанию показывать (это одна из главных пользы), но с переключателем.
- Очередь на телефоне с приоритетами: подсказка навигатора и ответ агента важнее уведомления. Во время активного манёвра (< 50 м до поворота) уведомления ждут.
- Отправка в очки пакетом из 4.3, текст обрезан до 60 символов по границе символа.
- Последние N уведомлений хранятся в памяти для контекста агента (этап 4), не дольше суток, не в облаке.
- iOS: уведомления на iPhone очки берут сами через ANCS, приложение их не пересылает. Это ограничение iOS, описать в README.
- **Результат:** уведомления из Telegram/SMS появляются на очках, Gadgetbridge не нужен.

### Этап 3. Звук с очков и распознавание речи

- Подписка на характеристику аудио (4.5), сборка потока по номерам пакетов, учёт потерь (подсчёт и интерполяция тишиной), **декодер IMA ADPCM на TypeScript** с восстановлением состояния из заголовка каждого пакета (так потеря одного пакета не ломает весь поток).
- Сохранение фразы в WAV 16 кГц 16 бит (для отладки и для диплома: экран «Записи» с прослушиванием и процентом потерь).
- Интерфейс `SpeechToText.transcribe(pcm, sampleRate) → { text, confidence }` с реализациями:
  - облачная по умолчанию: Yandex SpeechKit и OpenAI-совместимый Whisper API (выбор в настройках);
  - офлайновая запасная: Vosk (русская малая модель) или whisper.cpp через нативный модуль.
- Пока идёт запись и распознавание, на очки уходят статусы агента (4.6): «слушаю», «думаю».
- **Результат:** фраза, сказанная в очки, появляется текстом в приложении; в «Записях» видно процент потерянных пакетов.

### Этап 4. LLM-агент с инструментами

- Интерфейс `LlmProvider.chat(messages, tools) → { text } | { toolCalls }`. Инструменты описаны **один раз** в JSON Schema, адаптеры переводят их в формат конкретного API.
- Адаптеры: **OpenAI-совместимый** (покрывает OpenAI, DeepSeek, OpenRouter, локальные Ollama/LM Studio — по умолчанию), **GigaChat** и **YandexGPT** (доступны из РФ, нужны для демо на защите), Anthropic — по желанию. Выбор провайдера, модели и ключа — в настройках, ключи в Keychain/Keystore.
- В контекст запроса добавляются: текущее время, последние уведомления (этап 2), состояние навигации. Так агент понимает «перезвони ему» или «сколько ещё идти».
- Системный промпт требует ответ в JSON с двумя полями: `display` (≤ 60 символов, для очков) и `full` (полный ответ для истории в приложении). Если модель вернула не JSON — обрезать текст сам.
- Инструменты:

| Инструмент | Android | iOS | Подтверждение кнопкой |
|---|---|---|---|
| `navigate_to(query, profile?)` | вызывает этап 1 | то же | нет |
| `stop_navigation()` | | | нет |
| `set_alarm(time, label)` | интент `AlarmClock.ACTION_SET_ALARM` | локальное уведомление (AlarmKit на iOS 26+ — опционально) | нет |
| `call(contact)` | поиск в контактах + `ACTION_CALL` (разрешение `CALL_PHONE`) | `tel:` ссылка | **да** |
| `restart_pod(namespace, name)` | HTTPS POST на webhook из настроек | то же | **да** |
| `read_notifications(count?)` | из очереди этапа 2 | — | нет |

- **Подтверждение опасных действий:** на очки уходит запрос подтверждения (4.6, тип `CONFIRM`), например «Позвонить Маме? ДА=кнопка». Удержание D1 в течение 5 с — выполнить, иначе отмена. Без подтверждения опасный инструмент не выполняется никогда.
- `restart_pod`: телефон **не хранит доступ к кластеру**. Он делает POST на webhook (URL и токен в настройках) с телом `{ namespace, name }`; сам webhook (с узким RBAC) — вне этой задачи, но в `docs/` положи пример запроса и ожидаемого ответа.
- История диалога в приложении (поле `full`), на очках — `display` с прокруткой страниц коротким нажатием.
- **Результат:** «поставь будильник на семь», «позвони маме», «проведи до метро» работают голосом через очки; опасные команды требуют нажатия кнопки.

### Этап 5. Голос владельца

- Запись эталона: 3–5 фраз (20–30 с) **через микрофон очков**, не телефона — канал должен совпадать с рабочим.
- Модель диктора на устройстве (например, ECAPA-TDNN в ONNX Runtime Mobile или TFLite): эмбеддинг каждой фразы, средний вектор хранится зашифрованным ключом из Keystore/Keychain. **Отпечаток голоса никогда не покидает телефон** (биометрические персональные данные по 152-ФЗ). Перед записью — экран явного согласия.
- Каждая команда проверяется косинусной близостью с эталоном. Ниже порога — опасные инструменты (`call`, `restart_pod`) блокируются, безопасные работают.
- Экран калибровки для диплома: прогон набора записей, расчёт FAR/FRR и EER, экспорт в CSV.
- Кнопка «Удалить мой голос» стирает эталон полностью.
- **Результат:** чужой голос не может запустить звонок или рестарт пода.

### Этап 6. Замеры для диплома

Экран «Испытания» с экспортом в CSV: задержка «конец фразы → ответ на очках» (по этапам STT/LLM/BLE), процент потерь аудиопакетов, WER на наборе 20–30 команд, точность навигации (отклонение позиции от маршрута), число перестроений. Цифры не выдумывать: только измеренные приложением.

## 4. BLE-протокол О.Ч.К.О. (версия 1)

Задокументируй его в `docs/PROTOCOL.md` и реализуй кодеры/декодеры как чистые функции с тестами (в том числе тесты «байт в байт» с примерами из документа). Порядок байт — **little-endian**, строки — UTF-8 без нулевого терминатора, с длиной.

### 4.1. Сервис и характеристики

Базовый UUID: `1277XXXX-4f16-4cec-abf9-1d12f945b15b`, где `XXXX` — номер ниже. Все характеристики требуют шифрования и аутентификации.

| XXXX | Имя | Направление | Свойства | Назначение |
|---|---|---|---|---|
| `0001` | сервис О.Ч.К.О. | | | |
| `0002` | `display` | телефон → очки | Write (with response) | уведомления, навигация, ответы агента, статусы |
| `0003` | `events` | очки → телефон | Notify | кнопка, стартовое слово, батарея, ошибки |
| `0004` | `audio` | очки → телефон | Notify | ADPCM-кадры |
| `0005` | `control` | телефон → очки | Write (with response) | время, яркость, начало/конец записи, очистка экрана |
| `0006` | `info` | очки → телефон | Read | версия протокола, прошивки, возможности |

Стандартный Battery Service (`0x180F`) — дополнительно, если прошивка его поднимет; основной источник заряда — событие в `events`.

### 4.2. Общий заголовок пакета для `display`, `events`, `control`

```
offset size поле
0      1    ver      = 1 (версия протокола)
1      1    type     тип сообщения (таблицы ниже)
2      1    flags    бит0 = есть продолжение (фрагмент), бит1 = последний фрагмент, остальные 0
3      1    seq      номер сообщения 0..255 по кругу (у каждого направления свой)
4      ..   payload
```

Если сообщение не влезает в `MTU − 3 − 4` байт, приложение режет payload на фрагменты с одинаковым `seq` (флаги бит0/бит1). При MTU 247 почти все сообщения идут одним пакетом. Запись в `display` и `control` — строго последовательная очередь (следующая только после подтверждения предыдущей), с повтором при ошибке не более 3 раз.

### 4.3. `display`: типы сообщений

| type | Имя | Payload |
|---|---|---|
| `0x01` | `NOTIFY` | `app u8` (код иконки: 0 прочее, 1 SMS, 2 звонок, 3 мессенджер, 4 почта, 5 календарь), `prio u8` (0 обычный, 1 высокий), `ttl_s u8` (0 = до нажатия), `title_len u8`, `title`, `body_len u8`, `body` |
| `0x10` | `NAV_MANEUVER` | см. 4.4 |
| `0x11` | `NAV_PROGRESS` | см. 4.4 |
| `0x12` | `NAV_STATE` | см. 4.4 |
| `0x20` | `AGENT_STATE` | `state u8`: 0 нет, 1 слушаю, 2 думаю, 3 готово, 4 ошибка, 5 жду подтверждения |
| `0x21` | `AGENT_TEXT` | `ttl_s u8`, `len u8`, `text` (≤ 60 символов; листается коротким нажатием) |
| `0x22` | `CONFIRM` | `id u8`, `timeout_s u8`, `len u8`, `text` (вопрос, например «Позвонить Маме?») |
| `0x7F` | `CLEAR` | `layer u8`: 0 всё, 1 уведомления, 2 навигация, 3 агент |

**Приоритеты отображения на очках:** `CONFIRM` > `AGENT_*` > `NAV_*` (когда до манёвра < 50 м) > `NOTIFY` высокого приоритета > `NAV_*` > `NOTIFY`. Приложение тоже держит этот порядок у себя в очереди.

### 4.4. Навигационные пакеты

`NAV_MANEUVER` (0x10) — при смене текущего манёвра:

```
icon       u8   код манёвра (таблица ниже)
exit_no    u8   номер съезда с кольца (0 если не кольцо)
dist_m     u16  расстояние до манёвра в метрах, уже округлённое (0xFFFF = неизвестно)
total_m    u32  оставшееся расстояние до цели в метрах
eta_min    u16  оставшееся время в минутах
street_len u8
street     UTF-8, ≤ 24 байт (улица после манёвра; пусто если нет)
```

`NAV_PROGRESS` (0x11) — частые обновления, только числа:

```
dist_m   u16
total_m  u32
eta_min  u16
```

`NAV_STATE` (0x12):

```
state u8   0 выкл (очистить экран навигации), 1 маршрут строится, 2 ведение,
           3 перестраиваю, 4 нет GPS, 5 прибыли, 6 ошибка маршрута
```

Коды манёвров (`icon`), прошивка рисует по ним стрелки 24×24:

| код | манёвр | код | манёвр |
|---|---|---|---|
| 0 | нет / неизвестно | 8 | плавно налево |
| 1 | прямо | 9 | кольцо (с `exit_no`) |
| 2 | плавно направо | 10 | цель прибытия |
| 3 | направо | 11 | старт |
| 4 | резко направо | 12 | лестница / переход |
| 5 | разворот | 13 | держаться правее |
| 6 | резко налево | 14 | держаться левее |
| 7 | налево | 15 | паром / прочий транспорт |

Маппинг типов манёвров Valhalla → эти коды сделай отдельной таблицей в `src/nav/maneuverMap.ts`, сверь номера типов с документацией Valhalla (не по памяти) и покрой тестами. Неизвестный тип → 0 плюс текст инструкции в поле `street`, если улицы нет.

### 4.5. `audio`: ADPCM-кадры

Один кадр = 20 мс = 320 отсчётов 16 кГц = 160 байт IMA ADPCM. Одна GATT-нотификация — один кадр (этот канал без общего заголовка 4.2, ради экономии):

```
offset size поле
0      2    seq        номер кадра u16, по кругу
2      1    flags      бит0 = первый кадр фразы, бит1 = последний кадр фразы, бит2 = запущено стартовым словом (иначе кнопкой)
3      2    predictor  i16, состояние кодека на начало кадра
5      1    step_index u8 (0..88)
6      160  данные ADPCM, младший полубайт — первый отсчёт
```

Итого 166 байт. Приложение: собирает фразу от кадра с бит0 до кадра с бит1 (или до таймаута 1 с без кадров), пропущенные кадры заполняет тишиной и считает потери.

### 4.6. `events`: очки → телефон

| type | Имя | Payload |
|---|---|---|
| `0x01` | `BUTTON` | `kind u8`: 1 короткое, 2 удержание (начало), 3 отпускание, 4 двойное |
| `0x02` | `WAKEWORD` | — (стартовое слово распознано, дальше пойдёт аудио) |
| `0x03` | `CONFIRM_RESULT` | `id u8`, `result u8`: 1 да, 0 нет/таймаут |
| `0x04` | `BATTERY` | `percent u8`, `mv u16`, `charging u8` |
| `0x05` | `ERROR` | `code u8`, `len u8`, `text` |

### 4.7. `control`: телефон → очки

| type | Имя | Payload |
|---|---|---|
| `0x01` | `SET_TIME` | `unix u32`, `tz_min i16` (отправлять при каждом подключении) |
| `0x02` | `BRIGHTNESS` | `level u8` 0..255 |
| `0x03` | `AUDIO_CTRL` | `cmd u8`: 0 стоп записи, 1 старт записи (запись из приложения, например для эталона голоса) |
| `0x04` | `CONN_PARAMS` | `mode u8`: 0 экономный (длинный интервал), 1 быстрый (на время записи и активной навигации у манёвра) |

Сам запрос параметров соединения (интервал 15–30 мс при записи) инициирует прошивка; `CONN_PARAMS` — подсказка от приложения.

### 4.8. `info`

```
proto_ver u8, fw_major u8, fw_minor u8, fw_patch u8,
caps u16 (бит0 аудио, бит1 стартовое слово, бит2 навигационные иконки, бит3 кириллица)
```

Если `proto_ver` больше, чем знает приложение, — предупредить пользователя и работать в режиме совместимости (только `NOTIFY` и `CLEAR`).

## 5. Нефункциональные требования

- **Энергия очков важнее всего:** никаких периодических «пингов», только события и пакеты из правил выше.
- **Приватность:** отпечаток голоса и уведомления не уходят в облако; в облако (STT/LLM) уходит только то, что нужно для запроса, по TLS 1.2+. В настройках — явный список, какие данные куда отправляются.
- **Фоновая работа:** на Android один foreground service на подключение к очкам + навигацию (типы `connectedDevice` и `location`), корректные разрешения Android 14+ (`BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN`, `POST_NOTIFICATIONS`, `ACCESS_FINE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE_*`). На iOS — `bluetooth-central` и `location` в фоновых режимах.
- **Сеть:** все внешние сервисы (Nominatim, Valhalla, STT, LLM, webhook) — через настраиваемые URL, с таймаутами и понятными ошибками на очках («Нет сети»).
- **Логи:** отладочный экран с последними BLE-пакетами в hex (вход/выход) — сильно поможет при стыковке с прошивкой.

## 7. Порядок работы

- Начни с этапа 0 и этапа 1 и доведи навигатор до рабочего состояния с эмулятором до того, как браться за этапы 2–6.
- Если что-то в задаче противоречит API платформы или библиотеки — выбери разумный вариант, запиши решение в README в раздел «Принятые решения» и продолжай, не останавливаясь.
- Не выдумывай числа в документации и интерфейсе: всё, что не измерено, помечай как оценку.
