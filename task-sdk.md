# Задача: прошивка-SDK О.Ч.К.О. на MicroPython («тонкий» монитор)

Ты пишешь прошивку для смарт-очков О.Ч.К.О. (дипломный проект «Разработка модульной платформы бюджетных смарт-очков на основе серийных компонентов») на **MicroPython**. Прошивка оформляется как небольшой переиспользуемый **SDK**: модуль-библиотека `okko/` и короткий `main.py`, который его запускает.

Главная идея архитектуры: **очки ничего не решают сами**. Вся логика (уведомления, навигация, приоритеты, шрифты, кириллица, иконки, голосовой агент) живёт в мобильном приложении. Приложение присылает **готовую картинку** (весь кадр или его прямоугольник), очки её показывают и сообщают о результате. В обратную сторону очки отправляют только события: кнопку, аудио с микрофона, заряд, ошибки.

Приложение пишется параллельно (задача `app/task-react-native.md`). **BLE-протокол из раздела 4 — это контракт** между прошивкой и приложением. Менять его можно только с обновлением `docs/PROTOCOL.md` и номера версии протокола, «тихо» формат пакета не менять.

## 1. Железо

| Узел | Что | Подключение |
|---|---|---|
| Плата | **Seeed XIAO ESP32-C6** (RISC-V 160 МГц, 512 КБ SRAM, без FPU, 4 МБ flash) | |
| Экран | **OLED 0,42″ 72×40**, контроллер SSD1306, I2C, адрес `0x3C` | SDA = D4 (GPIO22), SCL = D5 (GPIO23) |
| Кнопка | одна тактовая кнопка на землю, внутренняя подтяжка | **D1 (GPIO1)**, активный уровень низкий |
| Микрофон | **INMP441**, I2S, моно (L/R на GND = левый канал) | SCK = D8 (GPIO19), WS = D9 (GPIO20), SD = D10 (GPIO18) |
| Питание | LiPo 401030, 130 мА·ч, выключатель в цепи BAT+ | |
| Антенна | на XIAO ESP32-C6 есть RF-переключатель: GPIO3 включает его, GPIO14 выбирает антенну (встроенная/внешняя) | **сверь уровни с вики Seeed** и выстави их в самом начале `main.py` |

Все номера пинов вынеси в `okko/config.py`, не разбрасывай по коду.

Оптика: OLED → линза → куб-светоделитель → глаз, поэтому кадр на экране **зеркальный**. Зеркалит прошивка, причём **аппаратно**, битами контроллера SSD1306 (segment remap `0xA0/0xA1` по горизонтали, COM scan `0xC0/0xC8` по вертикали). Процессор на это не тратится, а приложение всегда шлёт кадр в обычной ориентации. Какую ось зеркалить, задаётся в конфиге (по умолчанию горизонталь).

Заряд батареи: на XIAO ESP32-C6 нет штатного делителя на АЦП. Поддержи опциональный пин АЦП с делителем (`battery_adc_pin = None` по умолчанию). Если пин не задан, событие `BATTERY` не отправляется.

## 2. Платформа и ограничения (проверено по исходникам MicroPython)

- **MicroPython не ниже v1.27, рекомендуется v1.29.0**, сборка `ESP32_GENERIC_C6`. В v1.26 для C6 в `mpconfigboard.h` был выключен `machine.I2S` (микрофон не работал). С v1.27 I2S включён, а в `sdkconfig.base` стоит `CONFIG_ESP_SYSTEM_PMP_IDRAM_SPLIT=n`, поэтому работает нативный эмиттер RV32: `@micropython.native` и `@micropython.viper`.
- **Сжатие ADPCM пиши на `@micropython.viper`.** Чистый Python на 16 000 отсчётов в секунду не успевает. Оставь запасную реализацию на чистом Python (для тестов на ПК и на случай сборки без эмиттера) с тем же интерфейсом и одинаковым результатом байт в байт.
- **Стартовое слово на MicroPython не делаем.** Запись голоса запускает приложение (по удержанию кнопки), в `info` бит `CAP_WAKEWORD = 0`. Если позже понадобится KWS, это отдельный модуль на C, протокол к этому готов.
- **Параметры соединения прошивка запросить не может**: в модуле `bluetooth` MicroPython нет вызова для периферии. Пакет `CONN_PARAMS` прошивка принимает и подтверждает, но интервалом управляет приложение (на Android `requestConnectionPriority`). Запиши это в `docs/LIMITATIONS.md`.
- **MTU**: по умолчанию буфер характеристики в MicroPython 20 байт. Обязательно вызови `ble.gatts_set_buffer(handle, 512)` для `display` и `control`, `ble.config(mtu=247)`, а после подключения попробуй `gattc_exchange_mtu` (Android сам запросит 247, iOS обычно даёт 185). Текущий MTU отслеживай по `_IRQ_MTU_EXCHANGED`.
- **Энергопотребление MicroPython выше, чем у прошивки на C**: при активном BLE нет автоматического light sleep. Цель ≥ 3 ч от 130 мА·ч не гарантирована, её проверяют замером (этап 4). Все цифры, которые не измерены, помечай как оценку.
- Модули SDK компилируй в `.mpy` через `mpy-cross` той же версии (меньше RAM и быстрее старт). Для релиза опиши в README, как их «заморозить» в свою сборку прошивки.

## 3. Структура SDK и публичный API

```
firmware/
  main.py               // 10–20 строк: конфиг, Glasses(cfg).run()
  okko/
    __init__.py         // экспорт Glasses, Config
    config.py           // пины, тайминги, ориентация, имя устройства
    protocol.py         // константы и кодеры/декодеры пакетов, без зависимостей от железа
    packbits.py         // декодер (и эталонный кодер для тестов и приложения)
    gesture.py          // конечный автомат кнопки, без зависимостей от железа
    adpcm.py            // IMA ADPCM: viper + запасной чистый Python
    display.py          // драйвер SSD1306 72×40 + теневой буфер + системные экраны
    button.py           // пин + IRQ + gesture.py
    mic.py              // I2S INMP441 → кадры 20 мс
    bonds.py            // хранилище ключей бондинга во flash
    ble.py              // GATT-сервис, реклама, безопасность, очередь приёма
    sdk.py              // класс Glasses: связывает всё и диспетчеризует сообщения
  tests/                // тесты чистых модулей (CPython и MicroPython unix-порт)
  tools/
    client.py           // тестовый клиент на ПК (bleak): шлёт кадры, печатает события, пишет WAV
    frame_tool.py       // эталонная упаковка картинки/текста в FRAME (для приложения)
  docs/PROTOCOL.md
  docs/LIMITATIONS.md
  README.md
```

Модули `protocol`, `packbits`, `gesture`, `adpcm` (запасная часть) не импортируют `machine`, `bluetooth` и прочее железо. Их тестируют на ПК.

Публичный API (ориентир, можно улучшать):

```python
from okko import Glasses, Config

g = Glasses(Config())
g.on_message(CH_DISPLAY, 0x40, handler)   # расширение: свой тип пакета; handler(payload) -> статус
g.on_connect(cb); g.on_disconnect(cb)     # локальные хуки (например, мигнуть светодиодом)
g.send_event(type, payload)               # отправить произвольное событие с заголовком
g.send_error(code, text)
g.run()                                   # asyncio.run(...), не возвращается
```

«Универсальность» SDK означает таблицу обработчиков `(канал, тип) → функция`, а не цепочку `if`. Новый тип пакета добавляется одной регистрацией, без правки ядра.

## 4. BLE-протокол О.Ч.К.О. (версия 2)

Версия 2 заменяет версию 1 из `app/task-react-native.md`. **Что изменилось:**

- В `display` вместо смысловых пакетов (`NOTIFY`, `NAV_*`, `AGENT_*`, `CONFIRM`) появился один пакет `FRAME`: очки больше ничего не рисуют сами. Остался только `CLEAR`.
- В `events` добавлено `RESULT` (успех или ошибка обработки каждого пакета `display` и `control`). События `WAKEWORD` и `CONFIRM_RESULT` в прошивке на MicroPython не отправляются (коды зарезервированы).
- В `info` добавлены размеры экрана и новые биты возможностей.
- Каналы `audio`, заголовок пакета, UUID и `control` не изменились.

Порядок байт **little-endian**, строки UTF-8 без нулевого терминатора, с длиной.

### 4.1. Сервис и характеристики

Базовый UUID: `1277XXXX-4f16-4cec-abf9-1d12f945b15b`. Все характеристики требуют шифрования и аутентификации (флаги `_FLAG_*_ENCRYPTED | _FLAG_*_AUTHENTICATED`).

| XXXX | Имя | Направление | Свойства | Назначение |
|---|---|---|---|---|
| `0001` | сервис О.Ч.К.О. | | | |
| `0002` | `display` | телефон → очки | Write (with response) | кадры и очистка экрана |
| `0003` | `events` | очки → телефон | Notify | кнопка, результат, батарея, ошибки |
| `0004` | `audio` | очки → телефон | Notify | ADPCM-кадры |
| `0005` | `control` | телефон → очки | Write (with response) | время, яркость, запись звука, подсказка о режиме соединения |
| `0006` | `info` | очки → телефон | Read | версии, возможности, размер экрана |

Реклама: флаги + 128-битный UUID сервиса в advertising data, имя `OCHKO` в scan response (всё вместе не влезает в 31 байт).

### 4.2. Общий заголовок для `display`, `events`, `control`

```
offset size поле
0      1    ver      = 2
1      1    type
2      1    flags    бит0 = есть продолжение, бит1 = последний фрагмент, остальные 0
3      1    seq      0..255 по кругу, у каждого направления свой счётчик
4      ..   payload
```

Сообщение одним пакетом: `flags = 0`. Фрагменты одного сообщения имеют одинаковые `type` и `seq`, у всех, кроме последнего, `flags = 0x01`, у последнего `flags = 0x02`. Заголовок повторяется в каждом фрагменте, payload склеивается. Прошивка собирает сообщение до 1024 байт. Если пришёл фрагмент с другим `seq`, незаконченное сообщение выбрасывается, а хвост без начала даёт `RESULT` со статусом `FRAGMENT_ERROR`.

Прошивка принимает `ver` 1 и 2 для `CLEAR` и всех пакетов `control` (их формат не менялся). Для остальных при `ver ≠ 2` отвечает `RESULT` со статусом `BAD_VERSION`.

### 4.3. `display`

| type | Имя | Payload |
|---|---|---|
| `0x30` | `FRAME` | `x u8`, `page u8`, `w u8`, `h_pages u8`, `enc u8`, `data` |
| `0x7F` | `CLEAR` | `layer u8` (в v2 всегда очищается весь экран, поле оставлено для совместимости) |
| `0x40`–`0x6F` | резерв | для расширений через `on_message` |

**Формат `FRAME`.** Экран делится на 5 «страниц» по 8 строк. Прямоугольник задаётся столбцом `x` (0..71), первой страницей `page` (0..4), шириной `w` (1..72) и высотой в страницах `h_pages` (1..5); `x + w ≤ 72`, `page + h_pages ≤ 5`. Данные идут **в родном формате памяти SSD1306**: страница за страницей, внутри страницы `w` байт слева направо, в каждом байте бит0 = верхний пиксель столбца, 1 = пиксель горит. Это тот же формат, что `framebuf.MONO_VLSB`, поэтому прошивка просто копирует байты. Полный кадр: `x=0, page=0, w=72, h_pages=5`, 360 байт.

`enc`: `0` = как есть (`len(data) = w × h_pages`), `1` = PackBits. PackBits: байт `n` от 0 до 127 означает «следом `n+1` байт как есть», `n` от 129 до 255 означает «следующий байт повторить `257−n` раз», `n = 128` пропускается. Распакованный размер обязан быть ровно `w × h_pages`, иначе статус `DECODE_ERROR`.

Приложение само решает, слать весь кадр или изменившийся прямоугольник, и само выбирает `enc` (меньший из двух). Очки после применения прямоугольника сразу выводят его на экран.

### 4.4. `control` (как в v1)

| type | Имя | Payload |
|---|---|---|
| `0x01` | `SET_TIME` | `unix u32`, `tz_min i16` |
| `0x02` | `BRIGHTNESS` | `level u8` 0..255; `0` = выключить панель (команда `0xAE`), иначе контраст `0x81 level` и включить |
| `0x03` | `AUDIO_CTRL` | `cmd u8`: 0 стоп записи, 1 старт записи |
| `0x04` | `CONN_PARAMS` | `mode u8`: 0 экономный, 1 быстрый (прошивка только подтверждает, см. раздел 2) |

### 4.5. `events`: очки → телефон

| type | Имя | Payload |
|---|---|---|
| `0x01` | `BUTTON` | `kind u8`: 1 короткое, 2 удержание (начало), 3 отпускание после удержания, 4 двойное |
| `0x02` | `WAKEWORD` | резерв (MicroPython-прошивка не отправляет) |
| `0x03` | `CONFIRM_RESULT` | резерв |
| `0x04` | `BATTERY` | `percent u8`, `mv u16`, `charging u8` |
| `0x05` | `ERROR` | `code u8`, `len u8`, `text` |
| `0x06` | `RESULT` | `chan u8` (0 display, 1 control), `seq u8`, `type u8`, `status u8` |

`RESULT` отправляется **на каждое собранное сообщение** `display` и `control` после того, как оно применено (для `FRAME` это значит, что байты уже ушли в контроллер по I2C). GATT write response означает только «байты дошли», а `RESULT` означает «показано». Приложение ждёт `RESULT` перед следующим кадром, таймаут 1 с, повтор не более 3 раз.

Статусы `RESULT`:

| код | имя | когда |
|---|---|---|
| 0 | `OK` | |
| 1 | `BAD_VERSION` | неизвестная `ver` |
| 2 | `UNKNOWN_TYPE` | нет обработчика |
| 3 | `BAD_LENGTH` | короткий payload, длина данных не совпала, сообщение больше 1024 байт |
| 4 | `OUT_OF_BOUNDS` | прямоугольник за пределами экрана или нулевого размера |
| 5 | `DECODE_ERROR` | битый PackBits или неизвестный `enc` |
| 6 | `FRAGMENT_ERROR` | последний фрагмент без начала |
| 7 | `HW_ERROR` | исключение I2C или другая ошибка железа |

Коды `ERROR`: 1 потеря аудиокадров (в `text` число потерянных), 2 MTU мал для аудио (нужно ≥ 169), 3 ошибка микрофона, 4 ошибка дисплея, 5 внутренняя ошибка (в `text` класс исключения).

Кнопка: если двойное нажатие включено, короткое нажатие отправляется только после истечения окна двойного нажатия. Если второе нажатие превратилось в удержание, сначала уходит `1` (короткое), потом `2`.

### 4.6. `audio` (как в v1, без общего заголовка)

Один кадр = 20 мс = 320 отсчётов 16 кГц = 160 байт IMA ADPCM, одна нотификация на кадр:

```
offset size поле
0      2    seq        u16 по кругу
2      1    flags      бит0 первый кадр фразы, бит1 последний, бит2 запущено стартовым словом (в v2 всегда 0)
3      2    predictor  i16, состояние кодека на начало кадра
5      1    step_index u8 (0..88)
6      160  данные ADPCM, младший полубайт = первый отсчёт
```

Итого 166 байт, поток около 66 кбит/с. Кодек стандартный IMA ADPCM (таблица шагов из 89 значений, таблица индексов `-1,-1,-1,-1,2,4,6,8`). Каждый кадр декодируется независимо благодаря `predictor` и `step_index` в заголовке. Последний кадр фразы отправляется с `bit1` при `AUDIO_CTRL stop` или при разрыве записи. Если MTU < 169, запись не стартует и уходит `ERROR 2`.

### 4.7. `info`

```
proto_ver u8 (=2), fw_major u8, fw_minor u8, fw_patch u8,
caps u16: бит0 аудио, бит1 стартовое слово, бит2 иконки навигации, бит3 кириллица,
          бит4 FRAME, бит5 PackBits
width u8 (=72), height u8 (=40)
```

Для этой прошивки `caps = 0x0031` (аудио, FRAME, PackBits; аудио только при сконфигурированном микрофоне).

## 5. Требования к модулям

### 5.1. `ble.py`

- Низкоуровневый модуль `bluetooth` (без `aioble`, чтобы контролировать безопасность и буферы). Одно подключение. После разрыва снова реклама.
- Безопасность: `bond=True`, `le_secure=True`, `mitm=True`, `io = DISPLAY_ONLY`. На `_IRQ_PASSKEY_ACTION` с действием DISPLAY генерировать случайный 6-значный код, показывать его на OLED системным экраном и передавать в `gap_passkey`. Ключи хранить через `_IRQ_GET_SECRET` / `_IRQ_SET_SECRET` в файле во flash (`bonds.py`, по образцу `examples/bluetooth/ble_bonding_peripheral.py`). Сохранять при изменении, а не только при разрыве.
- Обработчик IRQ ничего не обрабатывает сам: копирует записанное значение (`gatts_read`) в очередь (ограниченную, например 8 элементов) и будит основную задачу через `asyncio.ThreadSafeFlag`. Переполнение очереди даёт `ERROR 5`.
- Отправка нотификаций через `gatts_notify` обёрнута в `try`: при ошибке стека пакет событий повторяется один раз, аудиокадр выбрасывается и учитывается в счётчике потерь.
- Интервал рекламы задаётся в конфиге (по умолчанию 300 мс).

### 5.2. `display.py`

- Свой драйвер SSD1306 под 72×40, без внешних библиотек. Эталон последовательности инициализации: U8g2 `ssd1306_72x40_er` (multiplex `0xA8 0x27`, charge pump `0x8D 0x14`, horizontal addressing `0x20 0x00`, `0xDA 0x12`, internal IREF `0xAD 0x30`). Смещение столбцов по умолчанию 28 (окно 72 из 128 по центру). Значения проверить на модуле и вынести в конфиг.
- Теневой буфер 360 байт в формате `MONO_VLSB` (тот же `bytearray` обёрнут в `framebuf.FrameBuffer` для системных экранов). `FRAME` копирует данные в буфер и отправляет на контроллер только этот прямоугольник: окно `0x21`/`0x22`, затем один `i2c.writevto` со всеми строками.
- Частота I2C 400 кГц.
- Системные экраны, которые прошивка рисует сама встроенным шрифтом `framebuf` 8×8 (латиница и цифры): код сопряжения, «нет связи» (по конфигу можно вместо этого гасить экран ради экономии), сообщение о фатальной ошибке. После подключения приложение обязано прислать полный кадр, прошивка старое содержимое не восстанавливает.
- Никаких аллокаций в пути `FRAME` после старта, кроме распаковки PackBits в заранее выделенный буфер.

### 5.3. `gesture.py` и `button.py`

- `gesture.py` — чистый конечный автомат: `update(pressed: bool, now_ms: int)` возвращает список событий. Время передаётся снаружи, чтобы тесты шли без железа.
- Тайминги в конфиге: debounce 30 мс, удержание 600 мс, окно двойного нажатия 300 мс. Окно `0` выключает двойное нажатие, тогда короткое уходит сразу при отпускании.
- `button.py`: прерывание по обоим фронтам будит задачу. Опрос каждые 5–10 мс идёт **только пока жест не завершён**, в покое задача спит на флаге и не крутит цикл.
- Учитывать переполнение `ticks_ms` (`time.ticks_diff`).

### 5.4. `adpcm.py` и `mic.py`

- I2S: `machine.I2S(0, ..., mode=I2S.RX, bits=32, format=I2S.MONO, rate=16000, ibuf ≥ 8 КБ)`, чтение через `asyncio.StreamReader(i2s).readinto()`. INMP441 выдаёт 24 бита в 32-битном слоте: в int16 перевести сдвигом (сдвиг в конфиге, по умолчанию 14, плюс насыщение).
- Перевод в int16 и сжатие одного кадра выполняются одной viper-функцией над готовыми буферами, без аллокаций.
- I2S инициализируется по `AUDIO_CTRL start` и отключается (`deinit`) по `stop` и при разрыве связи, чтобы микрофон не тратил энергию.
- Если микрофон не сконфигурирован или I2S не создаётся, бит аудио в `caps` сброшен, а на `AUDIO_CTRL` приходит `RESULT HW_ERROR`.

### 5.5. `sdk.py`

- `asyncio`: задачи приёма сообщений, кнопки, аудио, (опционально) батареи. Исключение в обработчике не роняет прошивку: в ответ `RESULT HW_ERROR` или `ERROR 5`, и цикл продолжает работать.
- Отдельные счётчики `seq` для `events` (общий заголовок) и `audio` (u16).
- При подключении: сбросить сборщики фрагментов, записать `info`, отправить `BATTERY` (если есть).
- Сторожевой таймер `machine.WDT` (по конфигу, по умолчанию 8 с) кормит основная задача.
- `machine.freq()`: по умолчанию не трогать. Вариант 80 МГц проверить замером на этапе 4 (аудио должно успевать).

## 6. Этапы

Каждый этап заканчивается проверяемым результатом. Делай их по порядку, внутри этапа маленькими осмысленными коммитами.

### Этап 0. Каркас, экран, кнопка

- Структура из раздела 3, `config.py`, `main.py`, RF-переключатель антенны.
- Драйвер дисплея: тестовая картинка, рамка по краю (проверка смещения 28 и 40 строк), зеркалирование по конфигу.
- Кнопка: события печатаются в REPL.
- **Результат:** на экране рамка без сдвигов, в REPL видны 1/2/3/4 на соответствующие жесты.

### Этап 1. BLE и протокол

- GATT-сервис, реклама, сопряжение с кодом на OLED, бондинг переживает перезагрузку.
- Приём `display`/`control` с фрагментацией, `FRAME` (raw и PackBits), `CLEAR`, `BRIGHTNESS`, `SET_TIME`, `CONN_PARAMS`, `RESULT` на каждое сообщение, `BUTTON` в `events`, `info`.
- `tools/client.py` на `bleak`: подключиться, прочитать `info`, отправить картинку из PNG 72×40 (через `tools/frame_tool.py`), отправить прямоугольник, напечатать все события и `RESULT`.
- **Результат:** с ПК и из nRF Connect картинка появляется на очках, на каждый пакет приходит `RESULT OK`, на заведомо битые пакеты приходят правильные коды ошибок.

### Этап 2. Микрофон и аудио

- `mic.py` + viper-ADPCM, `AUDIO_CTRL` start/stop, кадры 166 байт, флаги первого/последнего кадра, счётчик потерь.
- `tools/client.py` пишет принятую фразу в WAV (декодер ADPCM на Python).
- **Результат:** 10 секунд речи записываются в WAV без слышимых артефактов, потери кадров при MTU 247 и интервале 15–30 мс меньше 1 % (цифру измерить и записать).

### Этап 3. Надёжность

- WDT, восстановление после ошибок I2C (повторная инициализация дисплея), разрыв связи во время записи и во время приёма фрагментов, переполнение очереди.
- **Результат:** 30 минут в цикле «кадр раз в секунду + жесты кнопки + запись по 5 с каждую минуту» без перезагрузок и утечек памяти (`gc.mem_free()` в логе стабилен).

### Этап 4. Замеры для диплома

Измерить (USB-тестер или Nordic PPK2, способ описать) и свести в `docs/MEASUREMENTS.md`:

- ток в рекламе, в подключении без трафика, при кадре раз в секунду, при записи звука, с выключенной панелью (`BRIGHTNESS 0`);
- то же при `machine.freq(80_000_000)`;
- время от записи `FRAME` до `RESULT` (полный кадр и маленький прямоугольник, raw и PackBits);
- задержку от нажатия кнопки до события в приложении;
- расчётную автономность от 130 мА·ч по реальному сценарию.

Если цель 3 ч недостижима, в отчёте указать, какой узел съедает энергию и что даст переход на прошивку на C с тем же протоколом.

## 7. Тесты

- Чистые модули (`protocol`, `packbits`, `gesture`, запасной `adpcm`) покрыты тестами, которые запускаются **и в CPython (pytest), и в MicroPython unix-порту** той же версии.
- Тесты байт в байт по всем примерам из 4.8 (эти же примеры будут проверять кодеры в приложении).
- PackBits: распаковка(упаковка(x)) = x на случайных данных, все виды битых входов дают `DECODE_ERROR`.
- Фрагментация: два, три фрагмента, потерянный фрагмент, чужой `seq` в середине, хвост без начала, превышение 1024 байт.
- `gesture`: короткое, двойное, удержание, второе нажатие с переходом в удержание, дребезг короче debounce, переполнение `ticks`.
- ADPCM: viper и чистый Python дают одинаковые байты на одном векторе (проверка на устройстве или в unix-порту с x64-эмиттером); синус 1 кГц амплитудой 16000 после кодирования и декодирования даёт SNR не ниже 25 дБ без учёта первых 50 мс (эталонная реализация на Python даёт около 28,6 дБ).

## 8. Нефункциональные требования

- **Энергия важнее всего:** никаких периодических «пингов» и активных циклов ожидания. Батарея отправляется при подключении и не чаще раза в 5 минут.
- **Память:** горячие пути (`FRAME`, аудио, кнопка) не создают объектов после старта. Буферы выделяются заранее.
- **Логи:** уровень в конфиге; при отладке в REPL печатаются входящие и исходящие пакеты в hex (так же, как в отладочном экране приложения), в релизе выключено.
- Язык комментариев и документации русский.

## 10. Порядок работы

- Начни с этапов 0 и 1: без них приложение нельзя стыковать с очками.
- Если что-то в задаче противоречит API MicroPython или железу, выбери разумный вариант, запиши решение в README в «Принятые решения» и продолжай. Если решение меняет байты на проводе, это новая версия протокола, и это нужно явно отметить.
- Не выдумывай числа: всё, что не измерено, помечай как оценку.
- Приложение по задаче `app/task-react-native.md` пока описывает протокол v1, где очки рисуют сами. Рендер экрана в v2 переезжает в приложение, поэтому эмулятор очков в приложении должен декодировать те же `FRAME`, что уходят в очки.
