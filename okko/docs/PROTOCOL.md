# BLE-протокол О.Ч.К.О., версия 2

Контракт между прошивкой (`okko/`) и мобильным приложением. Этот же файл кладётся в репозиторий приложения. Изменение байтов на проводе = новая версия протокола.

Реализация: `okko/protocol.py` (константы, кодеры, сборщик фрагментов), `okko/packbits.py`, эталонная упаковка кадров — `tools/frame_tool.py`. Примеры из 4.8 проверяются тестами `tests/test_protocol.py` байт в байт.


Версия 2 заменяет версию 1 из `app/task-react-native.md`. **Что изменилось:**

- В `display` вместо смысловых пакетов (`NOTIFY`, `NAV_*`, `AGENT_*`, `CONFIRM`) появился один пакет `FRAME`: очки больше ничего не рисуют сами. Остался только `CLEAR`.
- В `events` добавлено `RESULT` (успех или ошибка обработки каждого пакета `display` и `control`). События `WAKEWORD` и `CONFIRM_RESULT` в прошивке на MicroPython не отправляются (коды зарезервированы).
- В `info` добавлены размеры экрана и новые биты возможностей.
- Каналы `audio`, заголовок пакета, UUID и `control` не изменились.

Порядок байт **little-endian**, строки UTF-8 без нулевого терминатора, с длиной.

## 1. Сервис и характеристики

Базовый UUID: `1277XXXX-4f16-4cec-abf9-1d12f945b15b`. Все характеристики требуют шифрования и аутентификации (флаги `_FLAG_*_ENCRYPTED | _FLAG_*_AUTHENTICATED`).

| XXXX | Имя | Направление | Свойства | Назначение |
|---|---|---|---|---|
| `0001` | сервис О.Ч.К.О. | | | |
| `0002` | `display` | телефон → очки | Write (with response) | кадры и очистка экрана |
| `0003` | `events` | очки → телефон | Notify | кнопка, результат, батарея, ошибки |
| `0004` | `audio` | очки → телефон | Notify | ADPCM-кадры |
| `0005` | `control` | телефон → очки | Write (with response) | время, яркость, запись звука, подсказка о режиме соединения |
| `0006` | `info` | очки → телефон | Read | версии, возможности, размер экрана |

Реклама: флаги + 128-битный UUID сервиса в advertising data, имя `OCHKO` в scan response (всё вместе не влезает в 31 байт).

## 2. Общий заголовок для `display`, `events`, `control`

```
offset size поле
0      1    ver      = 2
1      1    type
2      1    flags    бит0 = есть продолжение, бит1 = последний фрагмент, остальные 0
3      1    seq      0..255 по кругу, у каждого направления свой счётчик
4      ..   payload
```

Сообщение одним пакетом: `flags = 0`. Фрагменты одного сообщения имеют одинаковые `type` и `seq`, у всех, кроме последнего, `flags = 0x01`, у последнего `flags = 0x02`. Заголовок повторяется в каждом фрагменте, payload склеивается. Прошивка собирает сообщение до 1024 байт. Если пришёл фрагмент с другим `seq`, незаконченное сообщение выбрасывается, а хвост без начала даёт `RESULT` со статусом `FRAGMENT_ERROR`.

Прошивка принимает `ver` 1 и 2 для `CLEAR` и всех пакетов `control` (их формат не менялся). Для остальных при `ver ≠ 2` отвечает `RESULT` со статусом `BAD_VERSION`.

## 3. `display`

| type | Имя | Payload |
|---|---|---|
| `0x30` | `FRAME` | `x u8`, `page u8`, `w u8`, `h_pages u8`, `enc u8`, `data` |
| `0x7F` | `CLEAR` | `layer u8` (в v2 всегда очищается весь экран, поле оставлено для совместимости) |
| `0x40`–`0x6F` | резерв | для расширений через `on_message` |

**Формат `FRAME`.** Экран делится на 5 «страниц» по 8 строк. Прямоугольник задаётся столбцом `x` (0..71), первой страницей `page` (0..4), шириной `w` (1..72) и высотой в страницах `h_pages` (1..5); `x + w ≤ 72`, `page + h_pages ≤ 5`. Данные идут **в родном формате памяти SSD1306**: страница за страницей, внутри страницы `w` байт слева направо, в каждом байте бит0 = верхний пиксель столбца, 1 = пиксель горит. Это тот же формат, что `framebuf.MONO_VLSB`, поэтому прошивка просто копирует байты. Полный кадр: `x=0, page=0, w=72, h_pages=5`, 360 байт.

`enc`: `0` = как есть (`len(data) = w × h_pages`), `1` = PackBits. PackBits: байт `n` от 0 до 127 означает «следом `n+1` байт как есть», `n` от 129 до 255 означает «следующий байт повторить `257−n` раз», `n = 128` пропускается. Распакованный размер обязан быть ровно `w × h_pages`, иначе статус `DECODE_ERROR`.

Приложение само решает, слать весь кадр или изменившийся прямоугольник, и само выбирает `enc` (меньший из двух). Очки после применения прямоугольника сразу выводят его на экран.

## 4. `control` (как в v1)

| type | Имя | Payload |
|---|---|---|
| `0x01` | `SET_TIME` | `unix u32`, `tz_min i16` |
| `0x02` | `BRIGHTNESS` | `level u8` 0..255; `0` = выключить панель (команда `0xAE`), иначе контраст `0x81 level` и включить |
| `0x03` | `AUDIO_CTRL` | `cmd u8`: 0 стоп записи, 1 старт записи |
| `0x04` | `CONN_PARAMS` | `mode u8`: 0 экономный, 1 быстрый (прошивка только подтверждает, см. раздел 2) |

## 5. `events`: очки → телефон

| type | Имя | Payload |
|---|---|---|
| `0x01` | `BUTTON` | `kind u8`: 1 короткое, 2 удержание (начало), 3 отпускание после удержания, 4 двойное |
| `0x02` | `WAKEWORD` | резерв (MicroPython-прошивка не отправляет) |
| `0x03` | `CONFIRM_RESULT` | резерв |
| `0x04` | `BATTERY` | `percent u8`, `mv u16`, `charging u8` |
| `0x05` | `ERROR` | `code u8`, `len u8`, `text` |
| `0x06` | `RESULT` | `chan u8` (0 display, 1 control), `seq u8`, `type u8`, `status u8` |
| `0x07` | `NOTIFY` | `category u8`, `title_len u8`, `title`, `msg_len u8`, `message` — уведомление iPhone, полученное очками через ANCS |

`RESULT` отправляется **на каждое собранное сообщение** `display` и `control` после того, как оно применено (для `FRAME` это значит, что байты уже ушли в контроллер по I2C). GATT write response означает только «байты дошли», а `RESULT` означает «показано». Приложение ждёт `RESULT` перед следующим кадром, таймаут 1 с, повтор не более 3 раз.

Статусы `RESULT`:

| код | имя | когда |
|---|---|---|
| 0 | `OK` | |
| 1 | `BAD_VERSION` | неизвестная `ver` |
| 2 | `UNKNOWN_TYPE` | нет обработчика |
| 3 | `BAD_LENGTH` | короткий payload, длина данных не совпала, сообщение больше 1024 байт |
| 4 | `OUT_OF_BOUNDS` | прямоугольник за пределами экрана или нулевого размера |
| 5 | `DECODE_ERROR` | битый PackBits или неизвестный `enc` |
| 6 | `FRAGMENT_ERROR` | последний фрагмент без начала |
| 7 | `HW_ERROR` | исключение I2C или другая ошибка железа |

Коды `ERROR`: 1 потеря аудиокадров (в `text` число потерянных), 2 MTU мал для аудио (нужно ≥ 169), 3 ошибка микрофона, 4 ошибка дисплея, 5 внутренняя ошибка (в `text` класс исключения).

`NOTIFY`: `category` — CategoryID из ANCS (0 прочее, 1 входящий звонок, 2 пропущенный, 3 автоответчик, 4 соцсети и мессенджеры, 5 календарь, 6 почта, 7 новости, 8 здоровье, 9 финансы, 10 геолокация, 11 развлечения). Заголовок не длиннее 48 байт, текст не длиннее 120, обрезка по границе символа UTF-8: событие целиком влезает в одну нотификацию при MTU 185. Очки шлют только новые уведомления (без флага PreExisting), что и когда показывать, решает приложение. На Android ANCS нет, события не будет: приложение читает уведомления само.

Кнопка: если двойное нажатие включено, короткое нажатие отправляется только после истечения окна двойного нажатия. Если второе нажатие превратилось в удержание, сначала уходит `1` (короткое), потом `2`.

## 6. `audio` (как в v1, без общего заголовка)

Один кадр = 20 мс = 320 отсчётов 16 кГц = 160 байт IMA ADPCM, одна нотификация на кадр:

```
offset size поле
0      2    seq        u16 по кругу
2      1    flags      бит0 первый кадр фразы, бит1 последний, бит2 запущено стартовым словом (в v2 всегда 0)
3      2    predictor  i16, состояние кодека на начало кадра
5      1    step_index u8 (0..88)
6      160  данные ADPCM, младший полубайт = первый отсчёт
```

Итого 166 байт, поток около 66 кбит/с. Кодек стандартный IMA ADPCM (таблица шагов из 89 значений, таблица индексов `-1,-1,-1,-1,2,4,6,8`). Каждый кадр декодируется независимо благодаря `predictor` и `step_index` в заголовке. Последний кадр фразы отправляется с `bit1` при `AUDIO_CTRL stop` или при разрыве записи. Если MTU < 169, запись не стартует и уходит `ERROR 2`.

## 7. `info`

```
proto_ver u8 (=2), fw_major u8, fw_minor u8, fw_patch u8,
caps u16: бит0 аудио, бит1 стартовое слово, бит2 иконки навигации, бит3 кириллица,
          бит4 FRAME, бит5 PackBits, бит6 ANCS
width u8 (=72), height u8 (=40)
```

Для этой прошивки `caps = 0x0071` (аудио, FRAME, PackBits, ANCS; аудио только при сконфигурированном микрофоне, ANCS при `cfg.ancs`).

## Уточнения реализации (не меняют байты на проводе)

- `AUDIO_CTRL start` при MTU < 169: уходит `ERROR 2 "MTU"`, затем `RESULT HW_ERROR`.
- `AUDIO_CTRL` с `cmd` не 0/1: `RESULT BAD_LENGTH`.
- Переполнение очереди приёма (8 записей): лишняя запись выбрасывается без `RESULT` (приложение повторит по таймауту), уходит `ERROR 5 "rx overflow"`.
- Сообщение длиннее 1024 байт: один `RESULT BAD_LENGTH` с его `seq`, остальные фрагменты этого `seq` молча выбрасываются.
- Потерянный средний фрагмент не обнаруживается по флагам; для `FRAME` его ловит проверка длины (`BAD_LENGTH`/`DECODE_ERROR`).
- Потери аудиокадров отправляются одним `ERROR 1` с числом в `text` после окончания фразы.
- Исключение в обработчике: `RESULT HW_ERROR`; если это не `OSError`, дополнительно `ERROR 5` с именем класса.
