# Сервер О.Ч.К.О.

Бэкенд для мобильного приложения (`../client`) — сюда вынесена вся «умная»
часть и внешние интеграции, чтобы на клиенте остались только связь с модулем
и отправка картинок на очки:

- **LLM-агент** (`agent/`): цикл function-calling, промпт, история и разбор
  «второй/отмена» в `core.py`, `llm.py`, `tools.py`, `parsechoice.py`; сессии
  диалога — в `sessions.py`. Управляет навигацией через структурированные
  `actions`, которые клиент исполняет локально.
- **Геокодинг** (`navigation/geocode.py`, `navigation/localsearch.py`) — публичный
  Nominatim (1 req/s, кэш), локальный поиск с проверкой координат и обратное
  геокодирование точек карты.
- **Роутинг** (`navigation/router.py`) — публичный OSRM (1 req/s, ретраи),
  валидация ответа и ограничение пешего маршрута; маппинг манёвров —
  `navigation/maneuver_map.py`, полилиния — `navigation/polyline.py`.
- **Распознавание речи** (`speech/stt.py`) — интерфейс, провайдеры Этапа 3.
- **Прокси GigaChat** (`integrations/gigachat.py`) — держит `GIGA_CHAT_AUTH_TOKEN`
  и сертификат Минцифры вне бандла.

`main.py` в корне остаётся единственной точкой входа и FastAPI-обвязкой. Пакеты
сгруппированы по ответственности, а тесты повторяют их структуру:

```
server/
├── main.py
├── agent/          core.py, llm.py, tools.py, parsechoice.py, sessions.py
├── navigation/     geocode.py, localsearch.py, router.py, maneuver_map.py, polyline.py
├── integrations/   gigachat.py
├── speech/         stt.py
└── tests/          agent/, navigation/, integrations/, api/
```

FastAPI + uvicorn (сервер), aiohttp (запросы к GigaChat/Nominatim/OSRM).

```bash
cp .env.example .env   # вписать GIGA_CHAT_AUTH_TOKEN
uv run main.py         # http://0.0.0.0:8787
uv run pytest
```

## Эндпоинты

- `GET /health` — проверка доступности.
- `GET /chat` — обратная совместимость: проброс GigaChat `chat/completions` как есть.
- `POST /geocode` — локальный поиск адреса: `{"query", "position": {lat,lon}, "limit"}` →
  `{results[]}`. Без позиции — `400`; ближайшие результаты сортируются по расстоянию.
- `POST /route` — маршрут: `{"from", "to", "profile"}` → `{route}`. Пеший маршрут
  длиннее лимита — `422` с `code: "route_too_long"`.
- `POST /reverse-geocode` — адрес точки на карте: `{"lat", "lon"}` →
  `{result: {...}|null}`. Пустой `result` означает, что адрес не найден.
- `POST /agent` — сессионный диалог агента: `{"session_id"?, "user_text", "context": {position, nav_status}}`
  → `{session_id, reply: {display, full, candidates, actions}}`. `actions` клиент исполняет локально.
- `POST /stt` — распознавание речи (заглушка без ключей).

В приложении адрес задаётся `EXPO_PUBLIC_AGENT_PROXY_URL` (`client/.env`) или
полем на экране «Ассистент»; телефон и компьютер — в одной сети.

## Как работает агент

Сервер не просто проксирует запросы в GigaChat: он ведёт сессионный диалог,
выполняет function-calling, ищет адреса и строит маршруты. Клиент отправляет
текст и текущий контекст, а получает ответ и структурированные действия для
локального выполнения.

### Путь запроса

Клиент вызывает `POST /agent`:

```json
{
  "session_id": "id-предыдущего-диалога-или-null",
  "user_text": "Отведи меня на Тверскую, 1",
  "context": {
    "position": { "lat": 55.75, "lon": 37.61 },
    "nav_status": {
      "status": "navigating",
      "destinationName": "Тверская улица, 1",
      "remainingDistanceMeters": 650,
      "remainingDurationSeconds": 480,
      "nextManeuver": {
        "kind": "right",
        "streetNames": ["Тверская улица"],
        "distanceToManeuverMeters": 80
      },
      "routeProfile": "pedestrian",
      "gpsOk": true
    },
    "action_results": [
      { "type": "start_route", "status": "applied" }
    ]
  }
}
```

Эндпоинт в `main.py` восстанавливает агента по `session_id` или создаёт нового,
обновляет координаты и состояние навигации и передаёт запрос в `Agent.ask()`.
Для доступа к внешним сервисам создаётся `ServerNavPort`.

Перед обращением к модели агент собирает системную инструкцию, текущее время,
координаты пользователя, состояние навигации, ожидающие выбора адреса и историю
диалога. Клиент передаёт `nav_status` объектом с целью, остатком расстояния,
оценкой оставшегося времени, следующим манёвром, профилем маршрута и состоянием
GPS. Оценка времени пропорциональна пройденной доле маршрута. Старую строковую
форму (`idle`, `navigating` и т. п.) сервер тоже принимает —
`normalize_nav_status()` приводит оба варианта к одному виду.

В `action_results` клиент со следующим запросом передаёт результат выполнения
предыдущих действий: `applied` или `failed` с текстом ошибки. До успешного
ответа сервера результаты остаются в клиентской очереди, поэтому сетевая ошибка
не теряет их. Агент видит эти результаты в системном контексте и может учесть,
что действие на устройстве не выполнилось.

### Цикл function-calling

За один пользовательский запрос агент делает не больше четырёх шагов:

1. GigaChat возвращает текст или вызов функции.
2. Если модель выбрала функцию, сервер выполняет её сам.
3. Результат функции добавляется в историю и снова отправляется в GigaChat.
4. Когда модель возвращает обычный текст, он становится ответом пользователю.

`GigaChatProvider` использует модель `GigaChat`, температуру `0.3` и режим
`function_call: "auto"`. Схема сообщений и разбор ответов находятся в
`agent/llm.py`, сам цикл — в `agent/core.py`.

Доступные инструменты описаны в `agent/tools.py`:

- `navigate_to` — найти место и построить маршрут;
- `choose_destination` — выбрать один из найденных адресов;
- `stop_navigation` — остановить текущую навигацию;
- `get_navigation_status` — прочитать состояние навигации из контекста клиента.

### Поиск адреса и построение маршрута

При вызове `navigate_to` агент ищет адрес через `LocalSearch` поверх публичного
Nominatim. Позиция обязательна: без неё поиск возвращает `location_required`.
Сначала выполняются ограниченные запросы (`bounded=1`) в радиусах 2, 5 и 20 км
вокруг пользователя. Если они пусты, сервер определяет город через reverse
geocoding и повторяет запрос с названием города локально и глобально. Всего
делается не больше пяти поисковых запросов; reverse-запрос для города считается
отдельно и выполняется не более одного раза.

Каждый результат проверяется: координаты должны быть конечными и валидными,
дубликаты удаляются, всё дальше
`MAX_PEDESTRIAN_ROUTE_DISTANCE_METERS` (по умолчанию 20 км) отбрасывается.
Поэтому запрос «банк» из Тюмени не предложит банк в Омске. Если подходящий
адрес не найден за пять попыток, модель просит переформулировать запрос,
повторить позже или указать точку на карте в приложении.

Дальше возможны три случая:

- ничего не найдено — модель предлагает переформулировать запрос, повторить
  позже или выбрать точку на карте;
- найден один адрес — маршрут строится сразу;
- найдено несколько адресов — сохраняются до пяти кандидатов, и модель просит
  выбрать номер.

Короткие ответы «второй», «номер 3», «последний» и «отмена» разбираются без
обращения к LLM через `agent/parsechoice.py`. Более сложные формулировки снова идут
в GigaChat.

После выбора адреса `ServerNavPort` строит маршрут от текущей позиции через
публичный OSRM. По умолчанию используется профиль `pedestrian`. Пешеходный
маршрут длиннее 20 км отклоняется, как и ответ без двух корректных точек
геометрии или с нечисловым расстоянием. Лимит настраивается переменной
`MAX_PEDESTRIAN_ROUTE_DISTANCE_METERS` и не применяется к `bicycle` и `auto`.
Роутер преобразует ответ OSRM в координаты линии, манёвры, расстояние и
длительность. Затем агент добавляет для клиента действие `start_route`.

На карте приложения нажатие на здание или точку отправляет координаты в
`POST /reverse-geocode`, показывает адрес в карточке и предлагает построить
маршрут. Если Nominatim не вернул адрес, маршрут всё равно можно построить до
выбранной точки; название в этом случае — «Точка на карте».

### Ответ клиенту

Пример ответа:

```json
{
  "session_id": "идентификатор-диалога",
  "reply": {
    "display": "Маршрут: 1,2 км, 15 мин…",
    "full": "Полный текст ответа ассистента",
    "candidates": [],
    "actions": [
      {
        "type": "start_route",
        "destination": {},
        "route": {}
      }
    ]
  }
}
```

Поля `reply`:

- `full` — полный ответ для чата;
- `display` — сокращение примерно до 60 символов для экрана очков;
- `candidates` — адреса, если требуется выбор;
- `actions` — команды `start_route` и `stop_navigation`.

Сервер не меняет состояние мобильного приложения напрямую: клиент исполняет
`actions` через свой `navStore`, а текст `display` отправляет на очки.

### Сессии и память

Для каждой сессии создаётся отдельный `Agent`, который хранит:

- историю сообщений (максимум 20 записей);
- адреса, ожидающие выбора;
- действия, которые нужно вернуть клиенту.

`SessionStore` хранит сессии только в памяти процесса. Перезапуск сервера
удаляет историю диалогов и незавершённый выбор адресов; базы данных и
долговременного хранения сейчас нет.

### Подключение к GigaChat

При старте сервер читает `GIGA_CHAT_AUTH_TOKEN`, создаёт постоянную
`aiohttp`-сессию и подключает корневой сертификат Минцифры. OAuth-токен
кэшируется и обновляется заранее; при ответе `401` запрос один раз повторяется
с новым токеном. Этим занимаются `lifespan` в `main.py` и `GigaChatClient` в
`integrations/gigachat.py`.

Эндпоинт `/stt` не участвует в цикле агента и пока остаётся заглушкой.
